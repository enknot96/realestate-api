# 不動産業務管理API

不動産会社の業務（物件・問い合わせ・内見予約）を題材にしたバックエンドAPI。詳細な仕様は`不動産API_Hono_実装手順書_最終版.md`を参照。

## 今後の拡張案（既知の制約と設計判断）

### 顧客識別の精度向上（メール認証）

`POST /properties/:id/inquiries`は未認証・匿名で誰でも問い合わせできる公開エンドポイント。ここで送られてきた`email`を顧客の一意な識別子として扱い、`customers`テーブルをemail基準でupsertしている（同じemailなら同一人物とみなす）。

**既知の制約**: このエンドポイントには顧客の本人確認手段が存在しないため、同じメールアドレスを複数人が共有している場合（家族共用アドレス、会社の代表アドレスなど）、別人からの問い合わせが誤って同一顧客として扱われ、`customers.name`が意図せず上書きされる可能性がある。上書きが発生した場合はサーバーログに警告を出力するようにしている（`src/repositories/customerRepository.ts`の`upsertByEmail`）が、データの上書き自体は防げない。

**改修案**: メール認証（OTP・マジックリンクなど）を顧客に要求し、本人確認ができた場合のみ同一人物として扱う。ただし、これは顧客側にログイン・認証フローを追加することを意味し、「誰でも気軽に問い合わせできる」という公開エンドポイントの趣旨とはトレードオフになるため、今回のスコープでは見送った。

### レート制限（インメモリ実装の制約）

`POST /properties/:id/inquiries`（未認証で書き込める唯一の公開エンドポイント）には、IPごとに1分あたり5回までのレート制限をかけている（`src/middlewares/rateLimit.ts`）。

**既知の制約**: この実装はプロセス内メモリの`Map`でリクエスト回数を管理する、最もシンプルな方式。単一インスタンスで動かす分には機能するが、Vercelのようなサーバーレス環境では、リクエストごとに別インスタンス（別プロセス）が起動する可能性があり、その場合はインスタンス間でカウントが共有されず、実質的な制限が緩くなる（または効かなくなる）。

**改修案**: 本番運用では、Redis等の外部ストアにカウントを持たせる（Upstash Redisなど、サーバーレスと相性の良いマネージドサービスが候補）ことで、インスタンスをまたいだ一貫したレート制限が可能になる。
